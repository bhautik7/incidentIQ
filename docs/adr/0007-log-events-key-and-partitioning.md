# 7. LogEvents: bigint key, sampled rows, and no partitioning yet

Date: 2026-08-24
Status: Accepted

## Context

`log_events` is the only table in IncidentIQ whose design is driven by volume
rather than by meaning. At production scale it sees the highest insert rate, the
least interesting individual rows, and the shortest useful lifetime.

Three decisions had to be made together, because each one affects the others.

## Decision

**1. `bigint` identity key, not UUID.**

Every other entity uses a UUID, because its identifier appears in URLs, in API
responses and in Kafka messages, and because several writers create rows
concurrently. A log event has none of those properties: it is only ever reached
through its incident or its pattern. It would pay 8 extra bytes per row, plus 8
extra bytes in every index entry, for nothing.

Idempotency does not need the primary key. It is a separate `event_id uuid`
column, generated by the producing client and unique per organization - a
narrow, monotonic surrogate key and a wide, meaningful natural key, each doing
the job it is good at.

**2. A capped sample, not the full stream.**

`log_events` stores a bounded number of rows per pattern - first seen, last
seen, and a few in between. The authoritative total lives in
`log_patterns.occurrence_count`, incremented in the same transaction.

**3. Not partitioned yet.**

The table is a plain table. Retention is a `DELETE` by `occurred_at`.

## Consequences

The sampling decision is what makes the other two comfortable:

| | Store every line | Sample + counter |
|---|---|---|
| Rows/day at 1M events | 1,000,000 | ~15,000 |
| PostgreSQL growth/day | ~1.2 GB | ~20 MB |
| LLM calls/day | economically impossible | a few hundred |

At ~15,000 rows/day, partitioning would add monthly partition maintenance,
a composite primary key of `(occurred_at, id)`, and constraint-exclusion
subtleties, to solve a problem the table will not have for years.

**The trigger for revisiting:** `log_events` passing roughly 50M rows, or
retention deletes starting to cause noticeable bloat or autovacuum pressure.

**The migration path when that happens**, which is deliberately kept cheap:

1. Create `log_events_partitioned`, partitioned by `RANGE (occurred_at)`, with
   primary key `(occurred_at, id)` - PostgreSQL requires the partition key to be
   part of every unique constraint.
2. Copy data forward, then swap names in one transaction.
3. Replace retention `DELETE`s with `DROP PARTITION`.

Kafka's seven-day retention is the safety net that makes the swap low-risk: if
anything goes wrong, the recent window can be replayed.

Two properties of the current design keep that path open. The table is
**append-only** after classification, so there is no update traffic to
coordinate. And every index leads with `organization_id` and ends with a time
column, which is exactly the shape partition pruning wants.
